Core features

Monitoring

Monitoring is the first Web Fleet capability. The initial product will make a remote HTTP check trustworthy before layering broader website intelligence on top.

HTTP checks

A monitor will define a target URL, interval, timeout and expected response. Check results should retain enough detail to distinguish common failure classes instead of reducing everything to "down".

{
  "url": "https://example.com/health",
  "interval_seconds": 60,
  "timeout_seconds": 10,
  "expected_status": { "min": 200, "max": 399 },
  "follow_redirects": true
}

Useful failure classification

  • DNS resolution failure
  • connection refused/unreachable
  • TLS handshake or certificate failure
  • request timeout
  • redirect policy failure
  • unexpected HTTP status

From failures to incidents

One failed request should not necessarily create an incident. Web Fleet will use consecutive-failure and recovery rules so intermittent network noise does not become an alert storm.

healthy
  ↓ failed check
suspect
  ↓ threshold reached
incident open
  ↓ successful recovery threshold
recovered / incident closed

SSRF is part of the monitor design

Accepting arbitrary URLs creates a server-side request forgery boundary. Web Fleet must validate destinations, resolved addresses and redirect hops, and must defend against private/reserved targets and DNS rebinding. This is a first-version requirement, not post-release hardening.

Scheduling at fleet scale

Checks will use bounded concurrency and jitter. A fleet of 5,000 sites should not issue 5,000 requests on the same second merely because they share a one-minute interval.
