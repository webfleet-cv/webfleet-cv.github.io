Operate Web Fleet

Clustering

Run Web Fleet's fleet configuration as an explicitly replicated SQLite cluster using the shared Gantry Core Raft runtime.

Initial clustered surface

The first clustered surface is intentionally narrow: groups, sites and site tags are consensus-owned, along with stable cluster identities and durable replication operation state. Numeric SQLite row IDs remain local materialization details.

Monitoring/check history, incidents, audit and crawl observations, TLS/DNS/performance data, analytics, deployments, notification/webhook state, users/sessions/API tokens, launcher state and external side effects remain node-local in this first release. Raft replay never runs checks, crawls, notifications or webhooks.

Note: materializing a site also creates its default monitor, health row and security-header expectations on every replica as part of the consensus-owned site definition — those are replicated, not node-local. Anything those defaults subsequently observe (check results, history, incidents) stays node-local.

The older propagation subsystem remains separate from Raft replication. While clustering is enabled, propagation of site/request definitions is rejected so it cannot bypass consensus-owned fleet topology; monitor-definition propagation remains node-local and does not make monitor execution consensus-owned.

Authority and failure behaviour

standalone                 -> ordinary local fleet writes
replicated ready leader    -> Raft proposal
replicated ready follower  -> authenticated forward to leader
replicated unavailable     -> reject; never fall back to local SQL

A follower waits until the committed entry is locally applied before returning success. Idempotency-Key is carried as the durable operation identity so a retry cannot silently become a second fleet mutation.

Storage boundary

Clustered materialization is SQLite-only in the initial implementation. Enabling replication with PostgreSQL fails closed. A node must start clustering with a clean site/group configuration; automatic merging of independently populated Web Fleet databases is deliberately not supported.

Configuration

WEBFLEET_REPLICATION_ENABLED=true
WEBFLEET_REPLICATION_NODE_ID=wf-node-a
WEBFLEET_REPLICATION_LISTEN=10.0.0.10:7440
WEBFLEET_REPLICATION_BOOTSTRAP=true
WEBFLEET_REPLICATION_TLS_CERT=/etc/webfleet/replication.crt
WEBFLEET_REPLICATION_TLS_KEY=/etc/webfleet/replication.key
WEBFLEET_REPLICATION_TLS_CA=/etc/webfleet/replication-ca.crt

Production replication requires the complete cert/key/CA mTLS configuration. Plaintext is an explicit development/test opt-in only.

Pairing and voter membership

Gantry pairing and Raft membership are separate. Pair every replication participant using Web Fleet's cluster trust flow, then add voters explicitly. Pairing a node never silently grants it a consensus vote. webfleet replicate join rejects the request unless the target is an active, paired Gantry member that advertises the replication capability and a compatible protocol — an unpaired or disabled peer is refused before the Raft configuration changes, so an invalid join cannot make the cluster read-only.

webfleet replicate status --user admin@example.com --password '...'
webfleet replicate join --user admin@example.com --password '...' wf-node-b 10.0.0.11:7440
webfleet replicate snapshot --user admin@example.com --password '...'

The replication operator endpoints use the normal Web Fleet administrator session/CSRF boundary.

Quorum

Raft owns quorum. Three voters require two for authoritative writes; losing quorum makes fleet mutations fail closed. The implementation does not contain a three-node ceiling, and Web Fleet itself is locally certified at three voters (with a five-voter smoke certification also passing) through the same generic path used by the shared Gantry runtime. Real-infrastructure dogfood has not been performed yet, so no arbitrary-size production claims are made before that evidence exists.

Snapshots and recovery

Snapshots carry the consensus-owned group/site/tag state and durable operation identities. Restore reconciles existing clustered rows in place, preserving their local numeric IDs so node-local monitoring history is not destroyed merely by consensus recovery. Site deletion remains a real fleet deletion and therefore follows the normal dependent-data semantics.

Security model

Raft transport uses mTLS plus Gantry's pairwise peer credentials, identity binding, capability checks, replay protection and peer revalidation. Disabling or revoking a peer removes its replication authority; Raft voter membership remains a separate operator decision.
