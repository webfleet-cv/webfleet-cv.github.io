Getting started

Web Fleet is in active development. The first twenty implementation checkpoints now cover monitoring, performance, manual Audit, analytics and self-hosting foundations. There is still no public release or supported installer.

Current status: CP1 through CP10 are implemented in the development repository, but there is not yet a public release or supported installer. The source build already includes first-admin setup, grouped site inventory, fleet health, incidents, TLS, DNS, headers/redirects and bounded link crawling.

The five-minute goal

The target self-hosted experience remains three steps: install Web Fleet, create the first admin, and add a website URL. The development build already follows the second and third steps, and public monitoring requires no agent or code change on the monitored website.

# Planned installation flow
curl -fsSL https://web-fleet.github.io/install.sh | sh
webfleet serve

Open the dashboard, complete first-admin setup, then add a site such as:

Name:     Example
URL:      https://example.com
Interval: 60 seconds

What happens after adding a site

Web Fleet schedules guarded HTTP checks, records status and latency, classifies failures, derives a fleet-level health state, tracks coherent incidents, observes TLS/DNS/header/redirect state, and runs a separate bounded crawler for page/link health. Performance history, manual browser Audit and privacy-first analytics are implemented in development. Audit never runs automatically and history is opt-in.

Adding analytics later

Analytics is deliberately separate from public monitoring. A GitHub Pages site, static Nift site or application hosted on another provider can send pageview events to one central Web Fleet server.

<script
  defer
  src="https://fleet.example.com/tracker.js"
  data-site="site_public_id">
</script>

The planned default tracker does not require cookies or persistent visitor profiles.
